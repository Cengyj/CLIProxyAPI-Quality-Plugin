# CPA 状态与登录结果分离

版本：插件 0.29.5 / UI 13.6.5 / Runtime 2.2.1。

## 问题与原因

历史 2FA 登录失败后，“CPA 状态”会显示“OAuth 回调校验未通过，未交换或保存凭证”等登录诊断。

`plugin/login/accounts.go` 在同步终态任务时，将 `job.ErrorCode` 写入了账号的 `HealthReason`。`plugin/ui/login.js` 又将该字段兜底交给通用登录错误文案映射。因此一次登录失败会覆盖已有巡检说明，并在 CPA 状态和最近操作两处重复显示。

## 修复后的行为

- 失败任务继续更新最近操作、错误码、阶段、具体原因、待处理标记和自动登录失败计数，但不再覆盖已有 CPA 巡检原因。
- CPA 状态仅展开凭证状态及安全核对相关说明，不再使用通用登录错误映射。历史混写的 `invalid_callback`、密码/2FA 拒绝、运行时错误和登录限流等不会出现在该列或其悬停说明中。
- 历史错误仍保留在任务、日志和最近操作中。未执行数据库迁移，也未修改历史任务、凭证或账号资料。
- 未绑定账号即使因历史操作保存为 `unknown`，也显示“尚未绑定”。已有绑定的账号保留原有巡检状态，不会因登录失败被推断为正常或失效。
- 人工禁用、凭证缺失、身份变化、历史质量暂停及安全待核对仍可见；`security_pending` 优先显示简短的“安全操作待核对”。

## 验证与部署

修改前离线测试复现了 7 类凭证状态在手动/自动失败任务下被覆盖，共 14 个场景。修改后这些场景通过，插件全量测试、登录模块 race 测试和 36 项前端单元测试通过。

使用内存假账号检查历史污染字段，确认 CPA 状态列及悬停提示没有 OAuth 错误，最近操作仍有诊断，待处理筛选和安全待核对未丢失。浅色、白色、深色及手机布局通过；现有 111 项布局和账号弹窗交互检查通过。

Linux arm64 原生插件完成构建、加载及重启测试。官方 CPA 8.0.76 源码的 2413 个基线文件一致，宿主检查通过；需要网络环境的 WebRTC live 包仅编译。本机 8317 更新前执行停服备份，只替换插件库。升级前后的 2 个插件账号、7 条登录任务、1 次模型运行记录、1 条规则、1 份 CPA 凭证，以及配置、日志和宿主镜像均保持一致。验证未触发真实登录、重置 2FA 或模型请求。
